# Implementation Plan: Introduce HandlerContext for Tool Handlers

## 1. Goal

Today every tool `run` function receives `ToolRunContext`, which extends the MCP-specific `ToolContext` (carrying `_meta`, `sendNotification`, `sessionId`, etc.). This makes handler logic impossible to unit-test without a full `McpServer` + linked transport. The refactor introduces a lean `HandlerContext` that contains only what handlers actually need (`signal`, `resourceStore`, `elicitInput`, `log`, `onProgress`). The registration adapter in `defineTool` bridges `ToolContext` → `HandlerContext`; the public `DefinedTool<A,O>` interface gains a typed `handle` field usable directly in tests. All 18 tools are covered; no tool business logic changes.

### Current behavior

`ToolRunContext` (exported from `define-tool.ts`) extends `ToolContext` and adds `resourceStore`. All 18 tool `run` closures receive it. `runWithProgressSession` and `createBatchProgressCallbacks` take `ToolContext`. Testing any handler requires a full `createTestEnv()` call (McpServer + LinkedTransport + all 18 tools registered). `DefinedTool` is non-generic and has no `handle` field.
