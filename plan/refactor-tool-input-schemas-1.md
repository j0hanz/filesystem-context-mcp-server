# Implementation Plan: Flatten Tool Input Schemas & Cleanup Dead Validation

## 1. Goal

The MCP SDK rejects invalid tool inputs with the generic message `"Invalid input"` because [read](src/tools/read.ts) and [stat](src/tools/stat.ts) use top-level `z.union` schemas whose `invalid_union` issues have an empty path. The same shape also produces `inputSchema` JSON with top-level `anyOf` and no top-level `properties`, which causes MCP inspectors to hide the tools' fields. This refactor flattens both schemas to single `z.strictObject(...).superRefine(...)` schemas (per-field issues with rich paths, flat JSON Schema), removes a dead `safeParse` block in [defineTool](src/tools/define.ts#L100), and replaces [HashesSchema](src/tools/calculate-hash.ts#L44)'s custom `.refine + .superRefine` with native Zod v4 `z.record(z.enum(...), z.string().regex(...))`. Success is observed via inspector field rendering, per-field error messages for invalid inputs, and a passing `node scripts/tasks.mjs` run.

### Current behavior

`z.union([SingleReadSchema, BatchReadSchema])` in [read.ts](src/tools/read.ts) and `z.union([SingleStatSchema, BatchStatSchema])` in [stat.ts](src/tools/stat.ts) produce JSON Schema with top-level `anyOf` and no top-level `properties`. The MCP inspector reads `inputSchema.properties` and renders nothing. When the SDK validates `{}` against the union, Zod v4 emits an `invalid_union` issue with `path: []` and default message `"Invalid input"`, which the SDK forwards verbatim. [HashesSchema](src/tools/calculate-hash.ts#L44) layers `.refine` (key whitelist) and `.superRefine` (per-algorithm digest validation) on top of `z.record(z.string(), z.string())`; the JSON Schema does not surface the algorithm-name constraint to clients. [defineTool](src/tools/define.ts#L100) calls `def.input.safeParse(args)` after the SDK has already validated and rejected invalid inputs; this branch is unreachable.

## 7. Risks / Notes

|              ID               | Type | Detail                                                                                                                                                                                                                                                                       |
| :---------------------------: | :--: | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`RISK-001`](#7-risks--notes) | Risk | Tests that depended on the union shape via `z.infer<typeof StatInputSchema>` discriminated narrowing may need to switch to `'paths' in args` narrowing. Mitigation: existing handlers already use `'paths' in args`; verify by running the tool-level tests after each task. |
| [`RISK-002`](#7-risks--notes) | Risk | Strict object mode means previously-accepted unknown fields will now be rejected. Mitigation: the prior `.loose()` was only required because of the union — a flat object never needed loose mode. Verify no integration test sends unknown fields.                          |
| [`RISK-003`](#7-risks--notes) | Risk | Replacing the per-algorithm `z.hash(algo)` digest length check with a single hex regex weakens output validation. Mitigation: digests come from `node:crypto`, which always produces correct length; the regex is sufficient for the server-controlled value.                |
| [`NOTE-001`](#7-risks--notes) | Note | Do not change `outputSchema` for `read`, `stat`, or `calculate-hash`. Only inputs (read/stat) and the `hashes` field's value schema (calculate-hash) are in scope.                                                                                                           |
| [`NOTE-002`](#7-risks--notes) | Note | The `Invalid input` message is Zod v4's default for `invalid_union`; it cannot be made informative without removing the union. A future improvement could pass `error: ...` to a union, but flattening is strictly better because it also fixes inspector rendering.         |
| [`NOTE-003`](#7-risks--notes) | Note | The flattened `read` `superRefine` must reject `offset`/`length` when `paths` is provided (batch mode supports neither). Use `ctx.addIssue({ code: 'custom', path: ['offset'], message: "'offset' is not supported in batch mode" })`.                                       |
