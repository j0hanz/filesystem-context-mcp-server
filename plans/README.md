## Findings considered and rejected

So nobody re-audits these:

- `src/prompts.ts`: no findings above nitpick level. Handlers validate paths
  through `PathGuard`, wrap errors uniformly (`wrapHandler`), and block shell
  metacharacters in free-text args. Nothing worth a plan.
- Watcher ref-count over-count when the same client re-subscribes a URI with
  a fresh closure without unsubscribing: known, documented `ponytail:` ceiling
  at `src/core/watcher-registry.ts:28-32`, bounded by MAX_WATCHERS. Deferred
  by prior decision (see project memory) — not re-planned.
- Stdio listen watchers living until connection close (no per-stream teardown
  hook in the SDK's stdio listen router): documented ceiling in the
  `startServer` doc comment (`src/transport.ts:71-75`), bounded, single-client
  transport. By design.
- Legacy `resources/unsubscribe` fanning out to every contract regardless of
  subscription state (`src/resources.ts:606-617`): reachable only on stdio
  legacy era (single client); its ref-count side effects become harmless once
  Plan 001 lands (teardown no longer poisons future state). Not worth its own
  plan.
- `/healthz` exposing `process.uptime()` unauthenticated: trivial, standard
  practice for health endpoints.
- `desiredState` entries left as `'subscribing'` by subscribes that fail
  validation: residual micro-leak after Plan 001 (rare path, tiny strings).
  Accept; revisit only if per-subscription-id keying lands.
